# 2026-11-21（周六）· 白天：L4 关卡 2 结构化输出 · 夜间：L4 关卡 3 多轮与上下文记账

## 三句话复盘

1. **最大收获**：`strict` 的价值能用数字证明 —— 同一 prompt 20 次、**通过率 20/20**、`finish_reason` 全 `stop`；耗时中位 **9982.8 ms**，输入 token **恒 102**（说明 schema 走 `response_format` 传、**不占输入 token**），输出 token 每次 **381~2032**（差 5.3×，思考模式的 reasoning 计在 `completion_tokens` 里）。
2. **最大教训**：判据 ② 的三种破坏性输入**全部「通过」**，但那**什么都没证明** —— 坏输出在解码器就被封死了，我们的校验层一次都没被撞到。补了 `--guard` 负例注入（**0 次调用**）才拿到「3/3 判死 + 行列信息」的证据。**门没被撞过，就证明不了门结实**；这和「测试全绿但没写过失败的用例」是同一种错觉。
3. **明天第一步**：L4 关卡 3（成本与 prompt）第一块 —— 先把 `reasoning_tokens` 从 `completion_tokens` 里拆出来，否则「结构化输出一次多少钱」这个数根本算不准（今天的输出 token 波动 5.3 倍就是它造成的）。

## 今日沉淀

| 领域 | 内容 | 关键判据（可复测） |
|---|---|---|
| **两种 JSON 模式不是一回事** | `json_object` 只保证**能 parse**，不保证键名与类型（供应商原话「不同提示词或不同次调用结果可能不同」）；`json_schema` + `strict` 才**严格遵循 schema** | 同一任务用 `json_object` 跑 20 次，键名漂移会自己出现 |
| **strict 的两条硬条件** | ① `required` 必须覆盖**全部** `properties`（可空用 `["string","null"]` + 仍在 `required` 里）；② **每个 object 节点**都要 `additionalProperties: false` | 两条都能用代码判定，不需要"感觉合规" |
| **两家的 strict 口径不同** | OpenAI/Azure：全字段必填、每层 `additionalProperties: false`、关键字子集窄（不收 `minLength` / `pattern` / `minimum` / `minItems`）；阿里云百炼：可选字段**可以不进** `required`、关键字子集宽（但 `multipleOf` / `uniqueItems` / `patternProperties` 不收，直接 400） | ⇒ 写 schema 按**交集**，业务口径交给校验层，才不会被供应商锁死 |
| **`model_json_schema()` 不出 `additionalProperties`** | pydantic 2.14 只给 `type: "object"`；得自己递归补，**`$defs` 里的模型定义也算一个 object 节点**（嵌套模型走 `anyOf`/`$ref`，`items` 里是 `$ref` 不是 object） | 实测：`Enrollment` 顶层键是 `['description','properties','required','title','type']` |
| **`= None` 会静默改写契约** | pydantic 把「有默认值」当「非必填」⇒ 字段从 `required` 掉出去 ⇒ ① OpenAI strict 400 ② 本地 `model_validate_json` 开始放水（缺字段用默认值补上，照样"通过"）⇒ 20 次通过率**虚高** | 实测 `a: str; b: str \| None = None` → `required == ['a']`，`{"a":"x"}` 校验通过 |
| **`dict[str, X]` 在 strict 下表达不了** | 它的 `additionalProperties` 是**一个 schema**（`{"type":"string"}`）而不是布尔 `false`。把它覆盖成 `False` = 「只接受空对象」，语义反转且**不报错** | ⇒ 判据用「有没有 `properties`」而不是「`type == object`」；改写方向 = `list[KV]` 小模型 |
| **坏 JSON 只有一种异常** | `model_validate_json` 把 parse 失败也包成 `ValidationError`：`type == "json_invalid"`、`loc == ()`、`msg` 自带 `at line X column Y` | 一个 `except` 就能同时接「不是 JSON」和「字段不对」，不需要手动 `json.loads` |
| **pydantic 不查业务口径** | 实测 `{"name":"", "age":-3, "courses":[]}` **全部通过**（类上只有类型注解）⇒ 空姓名 / 负年龄 / 空课程必须自己补 | 这三条写进 `rule:` 前缀，与 `json:` / `schema:` 分桶统计 |
| **宽松模式会强转** | `"25"` → `25` 并接受；要判死得 `strict=True` / `StrictInt`，但本地口径就比发出去的 schema 更严 ⇒ 「失败」无法归因到模型 | 今天的取舍：**保持宽松**，把这一条写进笔记而不是偷偷改 |
| **schema 不占输入 token** | 20 次同 prompt 输入恒 **102**；四个不同 prompt 是 102 / 78 / 81 / 72，随 prompt 长度变、与 schema 无关 | ⇒ JSON Schema 是**约束**不是提示词，成本不在这边 |
| **`completion_tokens` 混着 reasoning** | 同 prompt 输出 381~2032（5.3×），耗时 6.9s~15.2s | ⇒ 关卡 2 的耗时/成本数字不能直接当「结构化输出成本」，关卡 3 必须拆 `reasoning_tokens` |
| **「解码器挡住」是推断不是实证** | 观测到 100% 合规 + 输出里保留 `\n  ,` 这类冗余空白（与"逐 token 生成"一致；后处理会规整掉） | 服务端实现未公开，**不能断定**是约束解码还是"后校验 + 重跑"；笔记里要写清是推断 |
| **负例注入 vs 真实调用** | 真实调用证明「上游在挡」；负例注入（0 成本）证明「校验层会红」 | 判据 ② 两半缺一不可：三种真实输入**全部通过**只是说明 strict 生效 |

# 夜间 · L4 关卡 3：多轮与上下文记账

## 三句话复盘

1. **最大收获**：`chat` 子命令四条判据一次跑绿 —— input **41 → 55 → 72 → 90** 单调递增，累计 **41 / 96 / 168 / 258** 与逐轮求和**全等**（差 0），重启打印「已读回 3 轮」、读回后首轮 input **90 > 72**，撞上限拿到原文 `Range of input length should be [1, 1048576]`。
2. **最大教训**：`output`（`completion_tokens`）里混着**思考 token**，而重发的历史只带 `content` ⇒ **每轮 input 的增量小于上一轮 output**（轮2 只涨 14，output1 = 28）。所以判据 ① 只能按「递增 / input3 > input1」判，用 `input3 − input1 ≥ output1 + output2` 会**误判为红**。
3. **明天第一步**：L4 关卡 4（成本与 prompt）—— 先把 `reasoning_tokens` 从 `completion_tokens` 里拆出来，否则「一次调用多少钱」算不准（今天的 input/output 比就是被思考 token 污染的）。

## 今日沉淀（夜间）

| 领域 | 内容 | 关键判据（可复测） |
|---|---|---|
| **API 无状态** | 服务端不存历史，每轮必须把 `user` + `assistant` 全量重发；`prompt_tokens` = **整段历史**的 token，不是这一句的 | 三轮 input 单调递增（41 → 55 → 72） |
| **两种「累计」别混** | 判据要的「累计上下文」= **Σ各轮 input**（反复重发的总读入量）；「会话当前占用」≈ 最后一轮 input + 最后一轮 output；「总消耗」= Σ(input+output)。三者口径不同，混了就白算 | 轮3 累计 168 == 41+55+72；若写成"最后一轮的值"是 72，一眼可辨 |
| **思考过程不进历史** | 拼回历史只带 `content`；`reasoning_content` 不重发 | 反证：轮2 input 增量 **14** < 轮1 output **28** |
| **落盘时机** | `save_turns` 必须在 `turns.append()` **之后**；写在之前 ⇒ 文件永远落后一轮，且 `exit` 会补存一次把问题藏住 | 聊 2 轮 → Ctrl+C → 文件应有 **2** 条（实现错时只有 1 条） |
| **覆盖写不是原子操作** | `open(path, "w")` 一打开就清空原文件；改 `*.tmp` + `Path.replace()`（同盘 rename） | 20 MB 文件 replace **0.823 ms**、`st_ino` / `st_mtime` 不变 ⇒ 是改名不是复制 |
| **异常要分层** | 落盘只接 `OSError`（磁盘/占用/权限）；其余异常冒泡（fail fast）。`except Exception` 会把代码 bug 报成"保存失败"，故障现场消失 | 故意让 `save_turns` 抛 `TypeError` → 应 traceback 而不是"保存失败" |
| **空文件 ≠ 损坏** | 空文件与截断文件同报 `JSONDecodeError: Expecting value`；先用 `path.stat().st_size == 0` 分开 | 空文件应打印「空历史」且**不**生成 `.corrupt` 文件 |
| **一次 stat 代替 exists + stat** | 两次系统调用之间有窗口（TOCTOU），文件恰好被删会让 `stat()` 抛到容错逻辑之外 | `try: path.stat() except FileNotFoundError: return []` |
| **Windows 上 rename 要求没人占用** | 文件被编辑器/杀毒/另一进程打开时，`replace` 抛 `PermissionError [WinError 5]`；POSIX 下开着句柄也能改名 | 持句柄 `replace` → WinError 5；关闭后成功 |

今天 `save_turns` 的落盘时机写错了一行（在 `append` 之前），而**打 `exit` 退出时一切正常** —— 因为退出会补存一次完整历史。是「模拟 Ctrl+C」才把「文件永远落后一轮」逼出来。同一条也适用于文档：`ruff` 全绿只证明"能跑"，不证明"崩了不丢"。
