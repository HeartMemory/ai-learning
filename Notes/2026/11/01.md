## 今日沉淀

| 领域 | 内容 | 关键判据（可复测） |
|---|---|---|
| **GIL 的本质** | CPython **默认构建**同一瞬间只有一个线程执行 Python 字节码 ⇒ 多线程在锁上**轮流**跑，不并行 | `sys._is_gil_enabled()` = **True**（3.14.8 实测）；4 个纯 Python 死循环：线程池加速比 ≈1，进程池 ≈ 4 |
| **`to_thread` 的边界** | **只把阻塞挪走，不把计算变快**；官方 Note 原文明写「typically only used to make **IO-bound** functions non-blocking」，只有释放 GIL 的 C 扩展或无 GIL 解释器才可用于 CPU 密集 | 10-31 的 **1.00 s** 成立是因为 `time.sleep` 属**IO 型等待**；换成 CPU 忙等只会更慢 |
| **线程池默认值** | 3.5 = CPU×5 ｜ 3.8–3.12 = `min(32, cpu_count()+4)` ｜ **3.13 / 3.14 = `min(32, (process_cpu_count() or 1)+4)`**（3.14 未再改） | 本机 `cpu_count` **20** / `process_cpu_count` **20** ⇒ `max_workers` = **24** |
| **为什么换 `process_cpu_count`** | `cpu_count()` 报**宿主机总量**；`process_cpu_count()` 报**本进程可用**（CPU 亲和性 / 容器 cgroup） | 容器限 2 核时前者照样报 64 ⇒ 会按宿主机开线程，纯抢 GIL |
| **抢占 vs 协作（补机理）** | 线程 = OS 时间片强制切（代码无法拒绝）；协程 = 只有代码 `await` 才切 | 10-31：串行 **2.02 s** vs `gather` **1.00 s**；单次切换 **≈10 µs** |
| **`asyncio.sleep` 到底睡谁** | **不睡任何线程** —— 往循环注册"定时器到期"回调后立刻让出，线程马上去跑别的任务 | `async def` 里用同步 `time.sleep` ⇒ `gather` 打回 **2.00 s**；`await asyncio.sleep` ⇒ **1.00 s** |
| **3.14 四个真变化** | ① `get_event_loop()` 无循环**抛 `RuntimeError`** ② **policy 系统弃用**（3.16 移除，改用 `asyncio.run(..., loop_factory=...)`）③ **`asyncio.iscoroutinefunction()` 弃用** ④ `create_task()` 接受任意关键字参数 | `asyncio.iscoroutinefunction` 用 `-W error::DeprecationWarning` 一跑**直接抛**（源码 `asyncio/coroutines.py:23` 的 `warnings._deprecated`）⇒ 弃用是真的，会告警 |
| **free-threading 的真实状态** | **PEP 779：3.14 起 officially supported**（3.13 的 PEP 703 是 experimental），但仍是**独立构建**（`Py_GIL_DISABLED`）；**默认构建照样带 GIL**，代价是单线程损失 **5–10%** | 实测 `gil_enabled = True` ⇒ 我们的 3.14.8 一切照旧 |
| **该并发什么（可迁移结论）** | **等外部 → 协程；算自己 → 进程**（除非库自己放 GIL） | 模型调用 / 检索 / 批量 embedding = IO ⇒ 并发收益大；本地分词 / 拼 prompt / 解析 JSON = CPU ⇒ 并发无收益 |
| **回访清单 +2** | #36 线程救不了 CPU 密集（GIL）｜#37 `time.sleep` 睡死的是事件循环那个线程 | 活跃 **24 → 26**（表头与表格实测行数一致） |
